GitHub Copilot Coding Agent

Delegate development tasks to Copilot and receive Pull Requests with implementations.

🎯 Learning Objectives

  • Understand when to use Copilot Coding Agent (Autocode)
  • Create well-structured GitHub Issues for Copilot
  • Assign issues to Copilot effectively
  • Review and iterate on Copilot's PRs
  • Handle different task complexities
🤖
What is Copilot Coding Agent?

The Coding Agent (formerly "Autocode") allows you to assign GitHub Issues directly to Copilot. It will:

  • Analyze the issue requirements
  • Create a new branch
  • Implement the solution
  • Open a Pull Request for your review
✅
Best Tasks for Coding Agent
  • Well-defined validation tasks - input checks, format validation
  • Bug fixes with clear reproduction steps
  • Simple CRUD endpoints
  • Test coverage additions
  • Documentation updates
  • Refactoring with clear patterns
⚠️
Less Suitable Tasks
  • Complex architectural decisions
  • Tasks requiring deep domain knowledge
  • Security-critical implementations
  • Vague or underspecified requirements
📋
Recommended Issue Structure

For best results, structure your issues like this:

## Task
[One clear sentence describing the goal]

## Context
[Background information about the feature/area]

## Requirements
- [ ] Requirement 1
- [ ] Requirement 2
- [ ] Requirement 3

## Acceptance Criteria
- [ ] Tests pass
- [ ] No TypeScript errors
- [ ] Follows existing patterns in [file]

## Implementation Hints
- Look at [similar file] for patterns
- Use [specific library/method]
- [Any other guidance]

Exercise 1: Simple Validation Task

1.1

Create an Issue for Copilot

Goal: Create a well-structured issue to prevent users from adding themselves as contacts.

Create a new issue with the following content:
▶ 📝 Issue Content 
## Title: Prevent users from adding themselves as contacts

## Task
Add validation to prevent users from creating a contact with their own userId.

## Context
Currently, the POST /contacts endpoint allows users to add anyone as 
a contact, including themselves. This creates confusing data and 
should be prevented.

## Requirements
- [ ] Add validation in `backend/contact-routes.ts`
- [ ] Return 400 status with clear error message
- [ ] Use existing validation patterns from the codebase

## Acceptance Criteria
- [ ] Cannot create contact with contactUserId === authenticatedUserId
- [ ] Returns: { error: "Cannot add yourself as a contact" }
- [ ] Status code: 400
- [ ] All existing tests pass
- [ ] Add unit test for this validation

## Implementation Hints
- See how other routes validate user input
- Check `backend/validators.ts` for validation patterns
- Test file: `src/__tests__/contacts.test.ts`
1.2

Assign Issue to Copilot

Goal: Assign the issue to Copilot using VS Code.

After creating the issue, go to the issue page
Click on "Assignees" in the sidebar
Select "Copilot" from the list

Or via VS Code with GitHub MCP:

▶ 💬 Assign via Chat 
Assign issue #[number] to Copilot in the [owner]/[repo] repository
What Happens Next
  • Copilot will analyze the issue
  • Create a new branch
  • Implement the solution
  • Open a PR (usually within minutes)
  • You'll receive a notification
1.3

Review Copilot's PR

Goal: Review and provide feedback on Copilot's implementation.

Open the PR created by Copilot
Review the code changes
If changes needed, comment with @copilot:
▶ 💬 Iteration Examples 
@copilot The error message should be more user-friendly. 
Change it to: "You cannot add yourself as a contact"
@copilot Add a test case for when contactUserId is undefined
@copilot Use the same validation pattern as in user-routes.ts

Exercise 2: Bug Fix Task

2

Create Bug Fix Issue

Goal: Create an issue for a bug that requires authentication.

▶ 📝 Bug Issue Template 
## Title: Add authentication check to /testData endpoint

## Bug Description
The `POST /testData` endpoint in `backend/testdata-routes.ts` is 
accessible without authentication. This should require a valid 
authenticated user.

## Steps to Reproduce
1. Start the backend server
2. Send POST request to /testData without auth header
3. Observe: Request succeeds (should fail with 401)

## Expected Behavior
- Return 401 Unauthorized when no valid auth token
- Return 403 if user doesn't have permission

## Requirements
- [ ] Add `ensureAuthenticated` middleware to the route
- [ ] Follow pattern from other protected routes
- [ ] Add test for unauthenticated access

## Implementation Hints
- See `backend/transaction-routes.ts` for auth pattern
- Middleware is in `backend/auth.ts`
Create the issue on GitHub
Assign to Copilot
Wait for PR and review

Exercise 3: Feature Implementation

3

Create Feature Issue

Goal: Create an issue for a new API endpoint.

▶ 📝 Feature Issue Template 
## Title: Add transaction statistics endpoint

## Task
Create a new endpoint that returns transaction statistics 
for the authenticated user.

## Requirements
- [ ] New endpoint: `GET /transactions/stats`
- [ ] Returns JSON with statistics
- [ ] Requires authentication

## Response Format
```json
{
  "totalSent": 1500.00,
  "totalReceived": 2300.00,
  "transactionCount": 15,
  "averageAmount": 253.33
}
```

## Acceptance Criteria
- [ ] Only counts user's own transactions
- [ ] Amounts are properly calculated
- [ ] Returns empty stats for new users
- [ ] Add integration test
- [ ] TypeScript types defined

## Implementation Hints
- Add route in `backend/transaction-routes.ts`
- Use existing transaction query patterns
- Add types in `backend/types.ts`
📊
Monitoring Copilot's Progress

Track Copilot's work on your issue:

  • Issue comments - Copilot posts status updates
  • Branch creation - Look for copilot- prefixed branches
  • PR notification - Email/GitHub notification when ready
  • VS Code - GitHub MCP can list open PRs

🔑 Best Practices

  • Write detailed issues - more context = better implementation
  • Include acceptance criteria - helps Copilot know when it's done
  • Reference existing patterns - point to similar code in the repo
  • Start with simpler tasks - build trust before complex features
  • Iterate with @copilot - treat it like code review with a colleague
  • Always review the PR - don't auto-merge without checking
